# bedolaga_updater

Поэтапное обновление [Bedolaga Bot](https://github.com/BEDOLAGA-DEV/remnawave-bedolaga-telegram-bot)
и механизм патчей — собственных правок поведения бота, которые переживают обновление.

```bash
curl -fsSL https://raw.githubusercontent.com/kifchandr/bedolaga_updater/main/bedolaga_updater | bash
```

Открывается меню:

```
    Обновить бота
  ❯ Управление патчами
    Очистка диска
    Выход
```

Перебор пунктов — `↑`/`↓` (или `k`/`j`), выбор — `Enter`, можно сразу нажать
цифру пункта. `q` или `Esc` — назад. Если терминала нет (cron, запуск без tty),
меню само переключается на ввод номера; принудительно — `PLAIN_MENU=1`.

Можно сразу в нужный раздел, минуя меню:

```bash
# сразу обновление
curl -fsSL https://raw.githubusercontent.com/kifchandr/bedolaga_updater/main/bedolaga_updater | bash -s -- update

# сразу патчи
curl -fsSL https://raw.githubusercontent.com/kifchandr/bedolaga_updater/main/bedolaga_updater | bash -s -- patches
```

В неинтерактивном запуске (cron, `NO_CONFIRM=1`) меню пропускается и сразу идёт
обновление — автоматизация работает как раньше.

## Очистка диска

В конце обновления, отдельной командой `cleanup` или пунктом меню «Очистка диска».
Чистятся три вещи, которые растут сами и однажды забивают диск.

**Кеш сборки docker.** Поэтапное обновление собирает образ на *каждую* версию,
и кеш копится прогонами — на боевом сервере он дорос до 38 ГБ. Штатный
`docker image prune` его не трогает: тот удаляет только висячие образы. Чистится
по порогу (`BUILD_CACHE_MAX_GB`, по умолчанию 10 ГБ), причём кеш свежее суток
остаётся — если обновление гоняют подряд, он экономит минуты на сборке. В итоге
в установившемся режиме на диске лежит кеш только последнего прогона.

**`logs/bot.log`.** Файл один и растёт без ограничений — 687 МБ на боевом
сервере. Ротация идёт через «скопировать и обнулить»: файл нельзя ни
переименовать, ни удалить, потому что бот держит его открытым и продолжил бы
писать в старый inode, а новый `bot.log` не появился бы до перезапуска.
Обнуление на месте безопасно — обработчик логов Python пишет в режиме дозаписи.
Архивы складываются в `logs/archive/` и удаляются через `LOG_RETENTION_DAYS`.

**json-логи контейнеров.** Docker их не ротирует, пока это не задано в
`daemon.json` или в compose. Раз не задано — подрезаем сами, когда переваливают
за `DOCKER_LOG_MAX_MB`.

```bash
curl -fsSL https://raw.githubusercontent.com/kifchandr/bedolaga_updater/main/bedolaga_updater | bash -s -- cleanup
```

## Режим техработ на время обновления

Перед установкой версий апдейтер проверяет режим техработ и включает его, если
он был выключен. В конце — после патчей и кабинета — выключает и перезапускает
бота. Если техработы были включены до запуска, скрипт их не трогает и в конце
не выключает: значит, их включили осознанно.

Отключить поведение целиком — `MAINTENANCE=0`.

### Почему пишется в два места

Признак включённости бот держит в настройке `MAINTENANCE_MODE` (таблица
`system_settings`), но **при старте не синхронизирует по ней своё состояние**:
`sync_with_settings` вызывается только из кабинета и Web API. В память состояние
поднимается из Redis-ключа `maintenance_status`, причём ручной режим
восстанавливается лишь тогда, когда настройка тоже говорит «включено».

Поэтому одной записи мало ни в БД, ни в Redis — апдейтер воспроизводит ровно ту
пару, которой бот сам хранит ручные техработы. Сначала Redis, затем настройка,
с откатом при сбое на половине: иначе осталось бы противоречие, при котором
кабинет включил бы техработы «сам по себе» при первом сохранении настроек.

Web API подошёл бы лучше — он применяет настройку на лету, без перезапуска, — но
его токены лежат в базе хешированными, а в `.env` токена может не быть вовсе.

### Если обновление оборвалось

Техработы останутся включёнными — это намеренно: сервис в неизвестном состоянии,
пускать туда людей рано. Скрипт об этом громко предупредит и подскажет команду:

```bash
curl -fsSL https://raw.githubusercontent.com/kifchandr/bedolaga_updater/main/bedolaga_updater | bash -s -- maintenance-off
```

## Зачем нужны патчи

Обновление бота — это `git checkout <тег>` в его папке. Любая правка в отслеживаемых
файлах бота (`main.py`, `app/**`) либо теряется при переключении тега, либо вовсе
роняет обновление сообщением «есть незакоммиченные правки». Поэтому патчи не трогают
git-дерево бота **вообще ни одним файлом**.

Вместо этого:

| Что | Где | Почему переживает обновление |
|---|---|---|
| Код патчей | `$BOT_DIR/patches/` | `.gitignore` бота начинается с `*` — любая новая папка игнорируется |
| Подключение | `$BOT_DIR/docker-compose.override.yml` | `.gitignore` бота игнорирует его явно («Local overrides — не коммитить!») |
| Настройки | `$BOT_DIR/patches/patches.env` | там же, плюс апдейтер его никогда не перезаписывает |
| Состояние | таблицы `patch_connect_reminders*` в БД бота | Alembic бота о них не знает и при миграциях не трогает |

`docker compose` подхватывает `docker-compose.override.yml` автоматически, без ключа `-f`.
Override монтирует `./patches` внутрь контейнера и подменяет команду запуска:

```yaml
services:
  bot:
    volumes:
      - ./patches:/app/patches:ro
    environment:
      BEDOLAGA_PATCHES: '1'
    command: ['python', '/app/patches/bootstrap.py']
```

`bootstrap.py` подключает патчи и запускает **тот же самый** `main.py`.

Из этого следует важное: после `git checkout` патчи остаются на месте сами по себе.
Апдейтер переустанавливает их в конце обновления не ради выживания, а чтобы подтянуть
свежие версии самих патчей — на случай, если новая версия бота потребовала их правок.

### Сломанный патч не роняет бота

Это заложено на трёх уровнях: `bootstrap.py` ловит любую ошибку подключения и всё равно
запускает `main.py`; реестр в `bedolaga_patches/__init__.py` изолирует патчи друг от
друга; фоновые задачи ловят исключения внутри цикла. Худший исход сломанного патча —
бот работает без него, а в логах лежит traceback.

Отключить патчи, не удаляя их (например, чтобы проверить, виноваты ли они):
в `docker-compose.override.yml` поставить `BEDOLAGA_PATCHES: '0'` и `docker compose up -d`.

## Работа с патчами

Пункт «2) Управление патчами» в главном меню, либо сразу:

```bash
curl -fsSL https://raw.githubusercontent.com/kifchandr/bedolaga_updater/main/bedolaga_updater | bash -s -- patches
```

```
  ❯ Установить / обновить патчи
    Включить / выключить патчи
    Показать статус
    Удалить патчи
    Назад
```

Состав патчей выбирается галочками — при установке и в разделе
«Включить / выключить»:

```
  ❯ [✓] Напоминание с инструкцией по подключению
    [ ] Отчёт по рефералам для конкурса в админ-панели
    [✓] Кнопка магазина внизу главного меню
    пробел — отметить · a — все · n — ничего · Enter — готово
```

`Пробел` ставит и снимает галочку, `a` отмечает все, `n` снимает все,
`Enter` подтверждает, `q`/`Esc` отменяют без изменений.

Файлы патчей скачиваются все — выбор управляет выключателями в `patches.env`.
Снятый патч не импортируется вообще, а передумать можно без повторной закачки.

Проверить, что патчи подключились:

```bash
docker logs remnawave_bot | grep bedolaga-patches
```

Ожидаемая строка: `[bedolaga-patches] подключены патчи: connect_reminder, contest_report, shop_button`

Настройки — `$BOT_DIR/patches/patches.env`. После правки:

```bash
cd "$BOT_DIR" && docker compose up -d
```

### Какие патчи есть

| Патч | Выключатель | Что делает |
|---|---|---|
| `connect_reminder` | `PATCH_CONNECT_REMINDER_ENABLED` | Шлёт инструкцию тому, кто за 10 минут после подписки ни разу не подключился |
| `contest_report` | `PATCH_CONTEST_REPORT_ENABLED` | Кнопка «🏆 Конкурс рефералов» в админке и команда `/contest_report` |
| `shop_button` | `PATCH_SHOP_BUTTON_ENABLED` | Кнопка-ссылка на магазин в главном меню, выше админки |

По умолчанию включены все. Выключатели живут в `patches.env`; меняются пунктом
«Включить / выключить патчи» или правкой файла вручную — значение `0` выключает.
Выключенный патч не импортируется вообще, то есть не может ни на что повлиять.

Состояние выключателей переживает обновление патчей, а выключатель нового патча
дописывается в `patches.env` автоматически, чтобы он не пропал из меню.

## Патч `connect_reminder` — инструкция по подключению

Если через 10 минут после создания подписки человек так и не подключился к VPN,
ему уходит ссылка на инструкцию:

- **в Telegram** — если он пришёл из бота (`users.telegram_id` заполнен);
- **на почту** — если он регистрировался через кабинет и Telegram у него нет
  (нужен подтверждённый `email_verified`).

### Как определяется «не подключился»

По полю `firstConnectedAt` панельного пользователя в Remnawave — это единственный
источник, который отмечает именно установленное VPN-соединение, а не отложенную
синхронизацию трафика.

Осторожность важнее скорости: если панель не ответила — по всем сразу или по одному
конкретному пользователю — напоминание не отправляется, а кандидат перепроверяется
на следующем проходе. Отправить инструкцию тому, кто уже подключился, хуже, чем
опоздать на минуту.

### Кого патч не трогает

- подписки моложе 10 минут (`DELAY_MINUTES`);
- подписки старше суток (`MAX_AGE_HOURS`) — защита от лавины после долгого простоя бота;
- подписки, созданные **до установки патча** (снимается через `BACKFILL=1`);
- статусы кроме `active` / `trial` / `limited`;
- подписки без панельного id;
- заблокированные и удалённые пользователи;
- те, кому уже отправляли: по умолчанию одно напоминание на человека за всё время
  (`ONCE_PER=subscription` — по одному на каждую подписку).

### Настройки

Все — в `$BOT_DIR/patches/patches.env`, см. `patches/patches.env.example`.

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `PATCH_CONNECT_REMINDER_ENABLED` | `1` | Включён ли патч |
| `PATCH_CONNECT_REMINDER_DELAY_MINUTES` | `10` | Через сколько минут проверять |
| `PATCH_CONNECT_REMINDER_URL` | ссылка на telegra.ph | Куда ведёт инструкция |
| `PATCH_CONNECT_REMINDER_INTERVAL_SECONDS` | `60` | Как часто идёт проход |
| `PATCH_CONNECT_REMINDER_MAX_AGE_HOURS` | `24` | Верхняя граница окна |
| `PATCH_CONNECT_REMINDER_BATCH` | `50` | Максимум напоминаний за проход |
| `PATCH_CONNECT_REMINDER_STARTUP_DELAY_SECONDS` | `90` | Пауза после старта бота (чтобы не мешать миграциям) |
| `PATCH_CONNECT_REMINDER_ONCE_PER` | `user` | `user` или `subscription` |
| `PATCH_CONNECT_REMINDER_BACKFILL` | `0` | Рассылать ли тем, кто подписался до установки патча |

Текст сообщений (ru/en) — в `patches/bedolaga_patches/connect_reminder.py`, словарь `MESSAGES`.

### Что писать в БД

```sql
-- кому уже отправляли и чем всё кончилось
SELECT state, channel, count(*) FROM patch_connect_reminders GROUP BY 1, 2;
```

Состояния: `sent` — отправлено, `connected` — успел подключиться, `no_panel_user` —
записи в панели нет, `no_channel` — ни Telegram, ни подтверждённой почты,
`failed` — бот заблокирован или письмо не ушло.

## Патч `contest_report` — отчёт по рефералам для конкурса

Кнопка «🏆 Конкурс рефералов» в админ-панели — сразу под «Промокоды/Статистика» —
и команда `/contest_report`.

Данные бота патч только читает (`SELECT`). Пишет он лишь в собственную таблицу
`patch_contest_report_periods` — историю введённых вручную периодов, чтобы их
можно было повторить кнопкой. Агрегат за период кешируется на 2 минуты: смена
сортировки, выгрузка CSV и оба вида билетов иначе гоняли бы один и тот же
тяжёлый запрос заново.

- Пресеты периода (7 / 30 дней, текущий / прошлый месяц) и свой период;
  последние введённые вручную периоды предлагаются кнопками — повторить
  прошлый расчёт можно одним нажатием.
- Сортировка топа переключается: по оплатам (умолч.) / приглашённым / доходу.
- CSV со сводкой и детализацией — по кнопке «📄 Выгрузить CSV», а не сам:
  при переборе периодов и сортировок файлы сыпались в чат пачками.
- Список билетов для розыгрыша: 1 билет = 1 реферал с покупкой либо
  1 приглашённый. Участник в файле — `@username`, а если его нет, то `id<telegram_id>`:
  раньше таких просто выбрасывали, и человек выигрывал конкурс, не участвуя в розыгрыше.
- Статистика по конкретному пользователю (`@username` или Telegram ID).

### Что именно считается

| Метрика | Определение |
|---|---|
| Пригласил | Рефералы (`users.referred_by_id`), зарегистрированные внутри периода |
| Оплатили | Из них те, чьё ПЕРВОЕ реальное пополнение (`transactions.type='deposit'`, завершённое, реальный платёжный метод, сумма ≥ `MIN_DEPOSIT_RUB`) попало в период (`scope=period`) или было когда угодно (`scope=all`) |
| Доход | Сумма всех реальных завершённых пополнений этих рефералов внутри периода |

Не считаются: незавершённые транзакции, начисления не типа `deposit`
(реферальные награды, возвраты), и методы из `NON_REAL_METHODS` — по умолчанию
`manual`, то есть ручное начисление админом.

### Настройки

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `PATCH_CONTEST_REPORT_ENABLED` | `1` | Включён ли патч |
| `PATCH_CONTEST_REPORT_TZ_OFFSET` | `3` | Часовой пояс дат и пресетов, часы от UTC |
| `PATCH_CONTEST_REPORT_MIN_DEPOSIT_RUB` | `100` | Минимальный депозит, засчитываемый как конверсия |
| `PATCH_CONTEST_REPORT_TOP` | `20` | Строк в топе сообщения (полный список — в CSV) |
| `PATCH_CONTEST_REPORT_SCOPE` | `period` | `period` или `all` |
| `PATCH_CONTEST_REPORT_NON_REAL_METHODS` | `manual` | Методы, не считающиеся реальным пополнением, через запятую |
| `PATCH_CONTEST_REPORT_BUTTON_TEXT` | `🏆 Конкурс рефералов` | Подпись кнопки в админке |
| `PATCH_CONTEST_REPORT_ANCHOR` | `admin_submenu_promo` | Под какой кнопкой админки встать |
| `PATCH_CONTEST_REPORT_RECENT_PERIODS` | `3` | Сколько прошлых периодов предлагать кнопками (0 — не хранить) |
| `PATCH_CONTEST_REPORT_CACHE_SECONDS` | `120` | Кеш агрегата за период, секунд (0 — выключить) |

Команда принимает те же параметры разово:

```
/contest_report 2026-06-01 2026-06-30 tz=3 min=100 top=20 scope=period
```

Даты — только `ГГГГ-ММ-ДД` (границы разделяются пробелом, поэтому время в них
не поддерживается). Конец периода включительно.

## Патч `shop_button` — кнопка магазина в главном меню

Добавляет в главное меню кнопку-ссылку (по умолчанию «💰 Наш магазин» →
https://ahrishop.com/) — **выше служебных строк** «Админ-панель» и «Модерация»,
а у обычного пользователя последней:

```
   💎 Подписка
   🎁 Промокод | 👥 Рефералы
   🆘 Поддержка
   💰 Наш магазин
   ⚙️ Админ-панель | 🖥 Веб-Админка
```

### Почему патч, а не штатная настройка

У бота есть свои кастомные кнопки главного меню (таблица `main_menu_buttons`,
заводятся через кабинет). Но в клавиатуре они встают **в середину** — перед
промокодом, рефералами, конкурсами и поддержкой, — и нужного места через них не
добиться. Патч вставляет строку уже в готовую клавиатуру, ориентируясь на
`callback_data` служебных кнопок (`admin_panel`, `moderator_panel`).

Если точное место не принципиально — штатная кнопка из кабинета решает ту же
задачу без патча и тоже переживает обновления (она в БД).

### Настройки

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `PATCH_SHOP_BUTTON_ENABLED` | `1` | Включён ли патч |
| `PATCH_SHOP_BUTTON_TEXT` | `💰 Наш магазин` | Подпись кнопки |
| `PATCH_SHOP_BUTTON_URL` | `https://ahrishop.com/` | Куда ведёт |

Ссылка проверяется перед отрисовкой: кнопка добавляется в каждое главное меню, и
битый URL Telegram отверг бы вместе со всем сообщением — человек остался бы без
меню. Всё, что не начинается с `http://` или `https://`, просто не рисуется, а в
лог уходит предупреждение.

Текстовый режим меню (`TEXT_MAIN_MENU_MODE`) патч не трогает: там reply-клавиатура,
а она не умеет кнопки-ссылки.

## Как добавить свой патч

1. Положить `patches/bedolaga_patches/<имя>.py` с функцией `install()`.
   Она вызывается один раз до запуска `main.py`; в ней монтируют обёртки
   вокруг нужных объектов бота.
2. Добавить `('<имя>', 'описание')` в `PATCH_MODULES` в
   `patches/bedolaga_patches/__init__.py`. Описание видно в меню апдейтера.
3. Добавить файл в `patches/manifest.txt`.
4. Добавить `PATCH_<ИМЯ>_ENABLED=1` с комментарием-описанием в
   `patches/patches.env.example` — строка комментария над переменной становится
   подписью в меню «Включить / выключить».
5. Запушить в этот репозиторий, затем на сервере выполнить `bedolaga_updater patches`
   → «Установить / обновить».

Правила, которые стоит соблюдать:

- **Импорты из `app.*` — как можно позже.** Внутри функций, а если без модульного
  импорта никак (декораторы, базовые классы FSM), то модуль обязан быть дешёвым:
  его импортируют в момент `install()`, до старта бота.
- **Следить за порядком, если патчите то, что импортируют по имени.**
  `from x import y` в чужом модуле копирует ссылку: пропатчить источник нужно
  ДО его импорта, а уже импортировавшим модулям — перепривязать имя вручную
  (см. `_patch_admin_keyboard` в `contest_report.py`).
- **Цепляться за singleton-сервисы и фабрики, а не за `main.py`.**
  `monitoring_service` удобен для фоновых задач, `app.bot.setup_bot` — для
  регистрации хендлеров.
- **Своё состояние — в свои таблицы** с префиксом `patch_`. Схему бота не трогать:
  её ведёт Alembic, и любое вмешательство переживёт ровно до следующей миграции.
- **Всё оборачивать в try/except.** Патч не имеет права ронять бота.

## Переменные окружения апдейтера

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `BOT_DIR` | автоопределение | Папка бота |
| `CABINET_DIR` | рядом с ботом | Папка кабинета |
| `TARGET_VERSION` | последняя | Обновляться до конкретной версии |
| `PG_USER` / `PG_DB` / `PG_CONTAINER` | из `.env` | Параметры БД |
| `BACKUP_RETENTION` | `10` | Сколько дампов хранить (`0` — не чистить) |
| `BACKUP_EVERY` | `1` | Бэкап перед каждой N-й версией |
| `MIN_FREE_MB` | `3000` | Порог свободного места |
| `PRUNE_IMAGES` | `1` | Выполнять очистку диска в конце обновления |
| `BUILD_CACHE_MAX_GB` | `10` | Выше этого размера чистить кеш сборки docker |
| `BUILD_CACHE_KEEP_HOURS` | `24` | Кеш свежее этого возраста не трогать |
| `LOG_MAX_MB` | `50` | Логи крупнее уходят в `logs/archive` |
| `LOG_RETENTION_DAYS` | `30` | Сколько хранить архивы логов |
| `DOCKER_LOG_MAX_MB` | `100` | json-логи контейнеров крупнее подрезаются |
| `NO_CONFIRM` | `0` | Не спрашивать подтверждений |
| `SKIP_BACKUP` | `0` | Пропустить бэкапы (не рекомендуется) |
| `DRY_RUN` | `0` | Только показать план |
| `MAINTENANCE` | `1` | Включать режим техработ на время обновления (`0` — не трогать) |
| `REDIS_CONTAINER` | `remnawave_bot_redis` | Контейнер Redis |
| `PATCHES` | `auto` | `auto` / `1` / `0` — переустанавливать ли патчи после обновления |
| `PATCHES_BASE_URL` | raw.githubusercontent этого репозитория | Откуда качать файлы патчей |
| `PLAIN_MENU` | `0` | `1` — меню без стрелок, вводом номера |
