# bedolaga_updater

Поэтапное обновление [Bedolaga Bot](https://github.com/BEDOLAGA-DEV/remnawave-bedolaga-telegram-bot)
и механизм патчей — собственных правок поведения бота, которые переживают обновление.

```bash
# обновить бота (и переустановить патчи, если они стоят)
curl -fsSL https://raw.githubusercontent.com/kifchandr/bedolaga_updater/main/bedolaga_updater | bash

# меню патчей: установить / статус / удалить
curl -fsSL https://raw.githubusercontent.com/kifchandr/bedolaga_updater/main/bedolaga_updater | bash -s -- patches
```

---

## Зачем нужны патчи

Обновление бота — это `git checkout <тег>` в его папке. Любая правка в отслеживаемых
файлах бота (`main.py`, `app/**`) либо теряется при переключении тега, либо вовсе
роняет обновление сообщением «есть незакоммиченные правки». Поэтому патчи не трогают
git-дерево бота **вообще ни одним файлом**.

Вместо этого:

| Что | Где | Почему переживает обновление |
|---|---|---|
| Код патчей | `$BOT_DIR/patches/` | `.gitignore` бота начинается с `*` — любая новая папка игнорируется |
| Подключение | `$BOT_DIR/docker-compose.override.yml` | `.gitignore` бота игнорирует его явно («Local overrides — не коммитить!») |
| Настройки | `$BOT_DIR/patches/patches.env` | там же, плюс апдейтер его никогда не перезаписывает |
| Состояние | таблицы `patch_connect_reminders*` в БД бота | Alembic бота о них не знает и при миграциях не трогает |

`docker compose` подхватывает `docker-compose.override.yml` автоматически, без ключа `-f`.
Override монтирует `./patches` внутрь контейнера и подменяет команду запуска:

```yaml
services:
  bot:
    volumes:
      - ./patches:/app/patches:ro
    environment:
      BEDOLAGA_PATCHES: '1'
    command: ['python', '/app/patches/bootstrap.py']
```

`bootstrap.py` подключает патчи и запускает **тот же самый** `main.py`.

Из этого следует важное: после `git checkout` патчи остаются на месте сами по себе.
Апдейтер переустанавливает их в конце обновления не ради выживания, а чтобы подтянуть
свежие версии самих патчей — на случай, если новая версия бота потребовала их правок.

### Сломанный патч не роняет бота

Это заложено на трёх уровнях: `bootstrap.py` ловит любую ошибку подключения и всё равно
запускает `main.py`; реестр в `bedolaga_patches/__init__.py` изолирует патчи друг от
друга; фоновые задачи ловят исключения внутри цикла. Худший исход сломанного патча —
бот работает без него, а в логах лежит traceback.

Отключить патчи, не удаляя их (например, чтобы проверить, виноваты ли они):
в `docker-compose.override.yml` поставить `BEDOLAGA_PATCHES: '0'` и `docker compose up -d`.

## Работа с патчами

```bash
curl -fsSL https://raw.githubusercontent.com/kifchandr/bedolaga_updater/main/bedolaga_updater | bash -s -- patches
```

Меню: установить/обновить, показать статус, удалить.

Проверить, что патчи подключились:

```bash
docker logs remnawave_bot | grep bedolaga-patches
```

Ожидаемая строка: `[bedolaga-patches] подключены патчи: connect_reminder`

Настройки — `$BOT_DIR/patches/patches.env`. После правки:

```bash
cd "$BOT_DIR" && docker compose up -d
```

## Патч `connect_reminder` — инструкция по подключению

Если через 10 минут после создания подписки человек так и не подключился к VPN,
ему уходит ссылка на инструкцию:

- **в Telegram** — если он пришёл из бота (`users.telegram_id` заполнен);
- **на почту** — если он регистрировался через кабинет и Telegram у него нет
  (нужен подтверждённый `email_verified`).

### Как определяется «не подключился»

По полю `firstConnectedAt` панельного пользователя в Remnawave — это единственный
источник, который отмечает именно установленное VPN-соединение, а не отложенную
синхронизацию трафика.

Осторожность важнее скорости: если панель не ответила — по всем сразу или по одному
конкретному пользователю — напоминание не отправляется, а кандидат перепроверяется
на следующем проходе. Отправить инструкцию тому, кто уже подключился, хуже, чем
опоздать на минуту.

### Кого патч не трогает

- подписки моложе 10 минут (`DELAY_MINUTES`);
- подписки старше суток (`MAX_AGE_HOURS`) — защита от лавины после долгого простоя бота;
- подписки, созданные **до установки патча** (снимается через `BACKFILL=1`);
- статусы кроме `active` / `trial` / `limited`;
- подписки без панельного id;
- заблокированные и удалённые пользователи;
- те, кому уже отправляли: по умолчанию одно напоминание на человека за всё время
  (`ONCE_PER=subscription` — по одному на каждую подписку).

### Настройки

Все — в `$BOT_DIR/patches/patches.env`, см. `patches/patches.env.example`.

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `PATCH_CONNECT_REMINDER_ENABLED` | `1` | Включён ли патч |
| `PATCH_CONNECT_REMINDER_DELAY_MINUTES` | `10` | Через сколько минут проверять |
| `PATCH_CONNECT_REMINDER_URL` | ссылка на telegra.ph | Куда ведёт инструкция |
| `PATCH_CONNECT_REMINDER_INTERVAL_SECONDS` | `60` | Как часто идёт проход |
| `PATCH_CONNECT_REMINDER_MAX_AGE_HOURS` | `24` | Верхняя граница окна |
| `PATCH_CONNECT_REMINDER_BATCH` | `50` | Максимум напоминаний за проход |
| `PATCH_CONNECT_REMINDER_STARTUP_DELAY_SECONDS` | `90` | Пауза после старта бота (чтобы не мешать миграциям) |
| `PATCH_CONNECT_REMINDER_ONCE_PER` | `user` | `user` или `subscription` |
| `PATCH_CONNECT_REMINDER_BACKFILL` | `0` | Рассылать ли тем, кто подписался до установки патча |

Текст сообщений (ru/en) — в `patches/bedolaga_patches/connect_reminder.py`, словарь `MESSAGES`.

### Что писать в БД

```sql
-- кому уже отправляли и чем всё кончилось
SELECT state, channel, count(*) FROM patch_connect_reminders GROUP BY 1, 2;
```

Состояния: `sent` — отправлено, `connected` — успел подключиться, `no_panel_user` —
записи в панели нет, `no_channel` — ни Telegram, ни подтверждённой почты,
`failed` — бот заблокирован или письмо не ушло.

## Как добавить свой патч

1. Положить `patches/bedolaga_patches/<имя>.py` с функцией `install()`.
   Она вызывается один раз до запуска `main.py`; в ней монтируют обёртки
   вокруг нужных объектов бота.
2. Добавить `<имя>` в `PATCH_MODULES` в `patches/bedolaga_patches/__init__.py`.
3. Добавить оба файла в `patches/manifest.txt`.
4. Запушить в этот репозиторий, затем на сервере выполнить `bedolaga_updater patches`
   → «Установить / обновить».

Правила, которые стоит соблюдать:

- **Ничего не импортировать из `app.*` на уровне модуля.** Только внутри функций —
  иначе патч утаскивает в момент старта половину бота.
- **Цепляться за singleton-сервисы, а не за `main.py`.** `monitoring_service` удобен
  тем, что main.py дёргает его и при старте, и при перезапуске цикла после сбоя.
- **Своё состояние — в свои таблицы** с префиксом `patch_`. Схему бота не трогать:
  её ведёт Alembic, и любое вмешательство переживёт ровно до следующей миграции.
- **Всё оборачивать в try/except.** Патч не имеет права ронять бота.

## Переменные окружения апдейтера

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `BOT_DIR` | автоопределение | Папка бота |
| `CABINET_DIR` | рядом с ботом | Папка кабинета |
| `TARGET_VERSION` | последняя | Обновляться до конкретной версии |
| `PG_USER` / `PG_DB` / `PG_CONTAINER` | из `.env` | Параметры БД |
| `BACKUP_RETENTION` | `10` | Сколько дампов хранить (`0` — не чистить) |
| `BACKUP_EVERY` | `1` | Бэкап перед каждой N-й версией |
| `MIN_FREE_MB` | `3000` | Порог свободного места |
| `PRUNE_IMAGES` | `1` | Чистить неиспользуемые образы в конце |
| `NO_CONFIRM` | `0` | Не спрашивать подтверждений |
| `SKIP_BACKUP` | `0` | Пропустить бэкапы (не рекомендуется) |
| `DRY_RUN` | `0` | Только показать план |
| `PATCHES` | `auto` | `auto` / `1` / `0` — переустанавливать ли патчи после обновления |
| `PATCHES_BASE_URL` | raw.githubusercontent этого репозитория | Откуда качать файлы патчей |
